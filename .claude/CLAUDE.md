# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Sergin.UserAccess is the UserAccess module (Postgres schema `ua`) for the **Sergin** platform — a .NET 10 modular monolith whose **MeterMinder** module is a Head-End System (HES) for smart electricity/gas/water meters. This module owns user identity/access: the `Users` and `Roles` aggregates. **It is also the authorization half of Keycloak sign-in** — SharedKernel authenticates the caller and calls this module's `IExternalIdentityResolver` implementation to find-or-create the local user and answer with the permissions they hold. Keycloak grants nothing; every permission comes from `ua`.

**This repo is embed-only.** There is no solution file, no `Directory.Build.props`/`Directory.Packages.props`, no dev config here — see `README.md` for why. It only compiles as a git submodule inside a host repo (today: [Sergin.MeterMinder](https://github.com/poursh/Sergin.MeterMinder)) that also provides a `Sergin.SharedKernel` submodule at the matching relative path. When working in this repo, assume you're editing it from inside that host checkout — `dotnet build`/`dotnet test` commands run against the *host's* solution file, not one in this repo.

## Per-project layering

- **`Sergin.UserAccess.Domain`** — aggregates/entities, strongly-typed IDs, repository interfaces. Depends only on `Sergin.SharedKernel.Domain`. Aggregates are built via a private/parameterless constructor + a `static Create(...)` factory method (e.g. `User.Create(UserName)`) — no public setters; mutate via named methods on the aggregate (e.g. `User.Deactivate()`).
  - ID generation always uses `Guid.CreateVersion7()`, never `Guid.NewGuid()` — e.g. `new UserInternalId(Guid.CreateVersion7())`.
  - `Create(...)` returns via **object-initializer syntax** against the private parameterless constructor (`new User { Id = ..., UserName = userName, IsActive = true }`), not a parameterized constructor call.
  - Strongly-typed IDs/value objects are declared as trailing `sealed record`s in the **same file** as their owning aggregate (e.g. `UserInternalId` and `UserName` both live in `User.cs`), not split into separate files.
- **`Sergin.UserAccess.Application.Contracts`** — the module's MediatR command/query request and response records only (e.g. `CreateUserCommand`, `CreateUserCommandResponse`, `GetUserByIdQueryCommand`, `UserQueryResponse`, `GetUserListItem`, `DeactivateUserCommand`, `DeactivateUserCommandResponse`), moved verbatim out of `.Application` — same namespace, same domain-typed constructor arguments, same `[RequiredPermissions]` attributes. References only `SharedKernel.Application` and this module's own `.Domain`. Exists so presentation layers (`.Presentation.WebApi`, `.Presentation.Blazor`) can depend on request/response shapes without pulling in handlers, repository interfaces, or `IUserAccessUnitOfWork` — those all stay in `.Application`. Carries `UserAccessApplicationContractsAssemblyReference`, exposing `typeof(...).Assembly` for `ISerginModule.ContractsAssembly`. See the [Sergin.MeterMinder](https://github.com/poursh/Sergin.MeterMinder) repo's `docs/superpowers/specs/2026-08-22-application-contracts-split-design.md` for the full design.
- **`Sergin.UserAccess.Application`** — MediatR handlers, query repository interfaces, `IUserAccessUnitOfWork`. References `.Application.Contracts` (added by the same split) for the request/response types its handlers implement `ICommandHandler<TCommand, TResponse>`/`IQueryHandler<TQuery, TResponse>` against. Feature folders hold the full slice under `<Aggregate>/Commands/<Feature>/...` — **queries live under `Commands/` too**, not a separate `Queries/` folder.
- **`Sergin.UserAccess.Infrastructure`** — write-side repositories (EF Core) and read-side query repositories (raw SQL via `IDbConnectionFactory`).
  - **Write-side repositories derive from SharedKernel's `EfRepository<TAggregateRoot, TId>`** (`Sergin.SharedKernel.Infrastructure.Data.EFCore.Repositories`): `UserRepository : EfRepository<User, UserInternalId>` and `RoleRepository : EfRepository<Role, RoleId>`, each passing its `IUserAccessDbContext` to the base. The base supplies `GetAsync`/`ExistsAsync`/`Insert`/`Remove` over `IDbContext.Set<T>()` — do not re-implement them here; the next `IRepository` member is a SharedKernel change, not one per module.
  - Aggregate-specific lookups (`GetByUserName`, `GetByExternalId`, `GetByName`) use the inherited `Set.SingleOrDefaultAsync(x => x.Field == value, cancellationToken)` and are added directly to the repository interface (`IUserRepository`, `IRoleRepository`). An alternate key answers `IUniqueKeyRepository<TKey>.IsTakenAsync` through the base's `protected AnyAsync(predicate, cancellationToken)` — `UserRepository.IsTakenAsync(UserName key)` is `AnyAsync(u => u.UserName == key, cancellationToken)`.
- **`Sergin.UserAccess.Infrastructure.Data`** — the module's `DbContext` (`UserAccessDbContext`, schema `ua`), `IEntityTypeConfiguration`s, value converters, migrations. `role_permissions` and `user_roles` are **owned collections** (`OwnsMany` + `HasField`/`PropertyAccessMode.Field` against the aggregate's private list), not separate aggregates — a permission has no life outside the role granting it. The `AddRolesAndExternalIdentity` migration also **seeds the `administrator` and `viewer` roles** with fixed ids, using one `InsertData` per row because CA1814 rejects the rectangular `object[,]` the scaffolder emits. **`ua.users.user_name` is unique** — `UserEntityTypeConfiguration` declares `HasIndex(u => u.UserName).IsUnique()` next to the `ExternalId` index, added by the `AddUserNameUniqueIndex` migration (`ix_users_user_name`). It is the guarantee behind `IUserRepository`'s `IUniqueKeyRepository<UserName>` and `CreateUserCommandValidator`'s advisory `MustBeUniqueIn` check (see Validation below); `ua.roles.name` already had one. Scaffolded migration `.cs` files are converted to a file-scoped namespace by hand (IDE0161 fails the build otherwise); the `.Designer.cs` is `<auto-generated />` and exempt. `UserAccessDbContext` also **opts into the outbox**: it implements `IOutboxDbContext` (`Sergin.SharedKernel.Infrastructure.Data.EFCore.Outbox`) and calls `modelBuilder.ApplyOutbox()` after `ApplyConfigurationsFromAssembly`, and the `AddOutbox` migration adds `ua.outbox_messages` and `ua.inbox_messages`. That opt-in is what makes `AddModuleDbContext` register this module's `IInbox<IUserAccessUnitOfWork>` and its `IOutboxRelaySource` for the host's `OutboxRelayService` to drain. No translator, integration event, or handler is declared here yet — the tables are ready for the first one (see the host repo's root `CLAUDE.md` Outbox bullet and its `docs/superpowers/specs/2026-09-13-outbox-design.md`).
- **`Sergin.UserAccess.Presentation.WebApi`** — minimal-API endpoints implementing `IEndpoint`.
- **`Sergin.UserAccess.Presentation.Blazor`** — Razor components for the Blazor Server UI (`Microsoft.NET.Sdk.Razor`). Feature-organized by aggregate under `<Aggregate>/Pages/`, with markup and code split into `.razor` and `.razor.cs` files. Each component exposes its navigation item through the module's `<Aggregate>Navigation` class, implementing `ISerginUiNavigation` to surface it on startup; the host reflects over modules' `UiAssembly` to collect them. Pages are also registered in the module's `NavItems` for routing. See **Blazor UI** section below for per-page conventions.
- **`Sergin.UserAccess`** (no-suffix composition root) — implements `ISerginWebApiModule` and `ISerginWebUiModule` from `Sergin.SharedKernel.Modules` (`UserAccessModule` class): `Schema`, `ApplicationAssembly`, `ContractsAssembly` (points to `Sergin.UserAccess.Application.Contracts`), `UiAssembly` (points to `Sergin.UserAccess.Presentation.Blazor`), `AddServices` (calls `AddModuleDbContext<TContext, TIContext, TIUnitOfWork>` plus per-aggregate `Add<X>Dependencies()`), `MigrateAsync`, `MapEndpoints` (per-aggregate `Map<X>Endpoints()`), and `NavItems` (list of UI navigation items collected from the Blazor project).

## CQRS split

- **Writes**: endpoint → MediatR `ICommand` → `ICommandHandler` → domain `AggregateRoot` factory/behavior method → `IRepository` (EF Core) → `IUnitOfWork.SaveChangesAsync`.
- **Reads**: query handlers use dedicated query-repository interfaces (`I<Feature>QueryRepository`) backed by **raw SQL through `IDbConnectionFactory`** (Dapper-style `QuerySingleOrDefaultAsync`/`QueryMultipleAsync`), bypassing EF entirely. A query handler maps a `null` result to `Error.NotFound()`.
  - Each query method opens its own `using DbConnection connection = await connectionFactory.CreateConnectionAsync();`.
  - SQL is a raw `"""..."""` string literal; snake_case columns are aliased to match the response record's exact property casing (`SELECT user_name AS userName FROM ua.users WHERE id = @Id;`).
  - List queries batch **two** statements through one `QueryMultipleAsync` call — `SELECT count(*) ...;` then the paged `SELECT ... LIMIT @PageSize OFFSET @Offset;` — read off the same `GridReader` (`ReadSingleAsync<int>()` then `ReadAsync<TItem>()`), wrapped as `new ListQueryResponse<TItem>(list, count)`.
- **The list-query feature carries its own request record.** `GetUserListQueryCommand` (`.Application.Contracts/Users/Commands/GetList/`) derives from `ListQuery<GetUserListItem>` (abstract, like every `ListQuery` type — the record is required, not optional), which already carries `IListQuery<TItem>`, so it can and does carry `[RequiredPermissions("permission.ua.users.read")]`; `GetUserListQueryCommandHandler` binds to it through `IListQueryHandler<GetUserListQueryCommand, GetUserListItem>`. `IGetUserListQueryRepository.GetListAsync` takes the **base** `ListQuery`, not the feature record — it only reads `Paggination`.
- **`.Produces<TResponse>()` is called on Create/GetList endpoints but omitted on GetOne endpoints.**
- **Endpoint route strings never include the schema segment** (`/users`, not `/ua/users`) — the host adds the schema prefix once via `MapGroup(module.Schema)`.

## Cross-cutting conventions

- **Results**: handlers return `ErrorOr<T>` (global-imported). Endpoints call `.ToApiResult()`.
- **Permissions**: `[RequiredPermissions("permission.ua.<resource>.<action>")]` on a command/query record — opt-in per slice, most commands have none.
- **Validation**: FluentValidation, at the pipeline — every write command has an `internal sealed class <Feature>CommandValidator : AbstractValidator<<Feature>Command>` in `.Application` next to its handler, discovered by `AddSerginCore`'s `ApplicationAssembly` scan and run by `ValidationPipelineBehavior` after the permission check. Three today: `CreateUserCommandValidator` (`UserName.Value` not empty, at most `UserName.MaxLength` = 100, **and `UserName` not already taken** — it takes `IUserRepository` through its constructor, which its scoped registration allows, and adds `RuleFor(x => x.UserName).MustBeUniqueIn(users).When(x => !string.IsNullOrWhiteSpace(x.UserName.Value))` from SharedKernel's `Validations/RepositoryRuleBuilderExtensions`; the rule targets the wrapper itself, so `Error.Code` is already `UserName` with no `OverridePropertyName`, the `.When` keeps the query from running once the shape rule has failed, and the check is advisory — the unique index on `ua.users.user_name` is the guarantee under a race), `DeactivateUserCommandValidator` (`Id` not `Guid.Empty`), and `ProvisionExternalUserCommandValidator`, which is **deliberately lenient** because it runs inside the OIDC callback where a failure fails the sign-in — it refuses only what the database would refuse anyway (empty `ExternalId`/`UserName`, `ExternalId` over `ExternalUserId.MaxLength` = 200, `Email` malformed or over `EmailAddress.MaxLength` = 320, `FirstName`/`LastName` over `User.NameMaxLength` = 200; no length on the username, whose column is unbounded and which Keycloak may fill with an email; no NotEmpty on the names, which the provider may omit). A refused provisioning surfaces through `ExternalIdentityResolver`'s `InvalidOperationException`, whose message is now FluentValidation's rather than Postgres's. **`ProvisionExternalUserCommandValidator` must never gain a `MustBeUniqueIn(users)` rule on `UserName`**: provisioning is find-or-create by `ExternalId`/`UserName` inside the OIDC callback, so on every returning user's sign-in the username *is* already taken — by the very row the handler is about to find — and a uniqueness rule there would refuse every login after the first. Rules target the value object's `.Value` and call `.OverridePropertyName(nameof(Command.Property))` so `Error.Code` names the command property (the API groups its `ValidationProblem` by it). **The `MaxLength` constants live on the value objects in `User.cs`** and are the single source for the validator, `NewUserFormModel`'s `[StringLength(Domain.Users.UserName.MaxLength, …)]` (qualified because the form model's own `UserName` property shadows the type inside the attribute) and `UserEntityTypeConfiguration`'s `HasMaxLength` calls — the column values did not change, so no migration. Queries have no validators; `Paggination` guards itself at construction. `CreateUserPage` calls `ErrorPresenter.Notify(result.Errors)` — every error, not `FirstError` — since validation yields one per broken rule.
- **Domain events**: `AggregateRoot` supports `Raise(IDomainEvent)`, but **no aggregate in this module calls it yet** — present-but-unused infrastructure.
- **Naming/sealing**: response records are `<Feature>CommandResponse` for commands, `UserQueryResponse` for a single-item query; list items are `GetUserListItem`. GetOne query/request records keep the blended `Get<Aggregate>ByIdQueryCommand` suffix even though they implement `IQuery<T>`. Application-layer commands/queries/responses are always `sealed record`; Presentation-layer `[FromBody]` request DTOs are plain `record`, not sealed. Handler classes are `internal sealed class`; **endpoint classes are `internal class`, never sealed**.
- **Strongly-typed IDs**: `record` wrappers (e.g. `UserInternalId(Guid)`) mapped to columns via EF value converters (see `Sergin.SharedKernel`'s `.claude/CLAUDE.md` for the converter template).
- **Database schema**: `ua`, set via `HasDefaultSchema` in `UserAccessDbContext` + a per-schema migrations history table. `UseSnakeCaseNamingConvention()` maps PascalCase members to snake_case columns.
- **User context**: under `Sergin:Auth:Mode=DevUser` the host builds one from configuration and the API side's `InternalUserContextFactory` still returns a `SYSTEM`/`ANONYMOUS` stub. Under `Mode=Keycloak` it is built from claims, and this module supplies the permissions in them — see the resolver below.
- **`ExternalIdentityResolver`** (`.Application/Users/Identity/`) implements SharedKernel's `IExternalIdentityResolver` by sending `ProvisionExternalUserCommand` through `ISender`, so provisioning is an ordinary feature slice with the usual unit of work and pipeline. It is `internal`, which is why `.Application` now carries an `InternalsVisibleTo("Sergin.UserAccess")`. **`ProvisionExternalUserCommand` must never gain a `[RequiredPermissions]` attribute** — it runs inside the OIDC callback before sign-in completes, when the ambient user context is still anonymous, so requiring a permission there fails every login.
- **Local variable typing**: declare a local as the narrowest interface its actual usage needs — e.g. `IReadOnlyCollection<T>` over `List<T>`. `UserQueryRepository.GetListAsync` materializes Dapper's `IEnumerable<T>` result as `IReadOnlyCollection<TItem> list = [.. await res.ReadAsync<TItem>()];`.
- Check each project's `GlobalUsings.cs` before adding `using` statements — many namespaces (`ErrorOr`, `Sergin.SharedKernel.*`) are already global.

## Blazor UI

Pages in `Sergin.UserAccess.Presentation.Blazor` follow these rules:

- **Route prefix is `/ua/`** — Razor `@page` directives are compile-time constants, so unlike minimal-API endpoints (which the host prefixes once via `MapGroup(schema)`), the schema prefix must be written into each page directive (e.g., `@page "/ua/users"`, `@page "/ua/users/new"`). A host-level startup route guard reflects over every module's `UiAssembly` and throws, naming any violating component. **Always match the module's schema in every `@page` string.**
- **`.razor` files contain markup only; all C# logic lives in `.razor.cs` code-behind.** Code inside `@code {}` blocks becomes part of generated output and escapes analyzer inspection, creating an unaudited hole in a repo where warnings-as-errors is enforced. Keep that hole empty.
- **Blazor pages inject `ISerginDispatcher` (`Sergin.SharedKernel.Presentation.Blazor.Dispatching`), never MediatR's `ISender`/`IMediator` directly.** In Blazor Server, "scoped" means the SignalR circuit's lifetime (hours), not a single HTTP request. Resolving MediatR's `ISender` off the circuit scope would share one `DbContext` across every user interaction, creating an unbounded change tracker, stale reads, and "a second operation was started on this context" errors on concurrent renders. `ISerginDispatcher.SendAsync(...)` opens a fresh DI scope per send, isolating each operation's `DbContext`. Inject it via `[Inject] ISerginDispatcher Dispatcher { get; set; }` in the code-behind (see `CreateUserPage.razor.cs`). **WebApi endpoints inject `ISender` directly** (see `CreateUserEndpoint`) — a minimal-API request already gets its own request-scoped DI container per call, so it has the same isolation for free without needing the dispatcher's fresh-scope trick.
- **List pages use `MudTable` with `ServerData` and paging only** — no sort, filter, or search controls. Not because the shared type lacks the fields: `ListQuery<T>` *does* carry `Term`, `Filtering` and `Sorting`. The plumbing below it drops them — `GetUserListEndpoint` passes all three into `GetUserListQueryCommand` and `UserListPage` passes none, but `UserQueryRepository.GetListAsync` binds only `PageSize`/`Offset` with a hardcoded `ORDER BY id`. So a control bound to any of them would silently do nothing, which is worse than omitting it; wiring them through is a read-side feature, not a UI change. Note that `MudTable`'s `TableState.Page` is 0-based while Sergin's `PageIndex` is 1-based — `UserListPage` passes `state.Page + 1` into `Paggination.Create` and says so in a comment.
- **`UserQueryResponse` carries `(Guid Id, string UserName)` only** — it has no `IsActive` field, even though `User.IsActive` exists in the domain and the `Deactivate()` command mutates it. The detail page cannot display the user's active state, and the deactivate action gives no pre-deactivation confirmation or post-action feedback beyond a snackbar notification. Widening the response record to include `IsActive` is a real API contract change belonging to its own query feature slice; it is not a simple omission to fix incidentally.

## `Roles` aggregate

`Sergin.UserAccess.Domain/Roles/Role.cs` — `AggregateRoot<RoleId>`, private ctor + `static Create(RoleName, IEnumerable<Permission>)`, with `Grant`/`Revoke` mutators. `RoleId` and `RoleName` are trailing records in the same file.

**The granted permission is `Sergin.SharedKernel.Domain.Securities.Permission` itself, not a module-local string type.** `Permission` was moved down from `.Application` into `SharedKernel.Domain` precisely so this aggregate could hold it: a `.Domain` project references only `SharedKernel.Domain`, so before the move the domain had to store a parallel `PermissionCode(string)` record and let the Application layer translate it at both ends. `PermissionCode` is gone; don't reintroduce it. Validation now happens where the value is constructed — `Permission.Create` guards the `permission.<parts>` format, and the read side uses `Permission.TryCreate` so a row whose format the code outgrew narrows the user's rights instead of failing their sign-in.

**EF maps the owned `role_permissions` rows straight onto `Permission`.** `RoleEntityTypeConfiguration.OwnsMany` writes `Permission.Value` to the `permission` column and EF materializes rows back through `Permission`'s private constructor — there is no value converter, and the `PermissionCodeConverter` that briefly existed alongside `RoleIdConverter`/`RoleNameConverter` was never wired up and has been deleted. The table shape is unchanged by the move; only the CLR type name in the migration snapshot differs.

**`Role.DefaultRoleName` (`"viewer"`) is assigned to every newly provisioned user.** A user created by first sign-in with no roles would hold no permissions and see an empty application, and this slice ships no admin screen to fix that. It is a constant rather than a configuration key on purpose — when role administration lands, that is the moment to make it configurable. There are **no** role CRUD feature slices, endpoints, or pages yet; changing who holds which role means editing `ua.user_roles` directly.

## `Users` aggregate

`Sergin.UserAccess.Domain/Users/User.cs` — `AggregateRoot<UserInternalId>`, private ctor + `static Create(UserName)` factory. `IsActive` defaults to `true` on creation and is flipped by the `Deactivate()` method. A second factory, `CreateFromExternalIdentity(...)`, builds the local record for a Keycloak-authenticated user, and `LinkExternalId`/`UpdateProfile`/`AssignRole`/`RevokeRole` mutate it afterwards. `ExternalId` (the provider's `sub`, unique, **nullable** — rows predating external sign-in have none, and `Create` still makes one without a provider), `Email`, `FirstName`, `LastName` and the owned `Roles` collection came with that.

Implemented feature slices (`Users/Commands/<Feature>/` in Application, mirrored in Infrastructure/Presentation):

| Feature | Kind | Route | Permission |
|---|---|---|---|
| `Create` | command | `POST /ua/users` | none |
| `DeactivateUser` | command | `POST /ua/users/{userId:guid}/deactivate` | none |
| `GetOne` | query | `GET /ua/users/{userId:guid}` | `permission.ua.users.read` |
| `GetList` | query | `GET /ua/users` (`[AsParameters] ListQueryRequestModel`) | none |
| `ProvisionExternalUser` | command | none — dispatched in-process from the OIDC callback | **none, and must stay none** |

Only `GetOne` carries a `[RequiredPermissions]` attribute — that's the current state of the module, not a rule that only reads need it. Add the attribute to new slices that should be protected; don't remove it from `GetOne` to "match" the others.

### Repositories

- `IUserRepository` (`Domain/Users/`) extends the generic `IRepository<User, UserInternalId>` with two named lookups, `GetByUserName(UserName)` and `GetByExternalId(ExternalUserId)` — the precedent for adding aggregate-specific lookups to the repository interface when generic CRUD isn't enough — and **also implements `IUniqueKeyRepository<UserName>`**, declaring `UserName` an alternate key of `User` through `IsTakenAsync(UserName)`. That declaration is what lets `CreateUserCommandValidator` call `.MustBeUniqueIn(users)`; `ExternalId` is unique in the database too but is deliberately not declared as a key, since no command takes one from a caller (provisioning finds-or-creates by it). Implemented by `UserRepository : EfRepository<User, UserInternalId>` in Infrastructure, which keeps only the two lookups and `IsTakenAsync`.
- Query repositories are split one-interface-per-feature (`IGetUserQueryRepository`, `IGetUserListQueryRepository`, plus a module-wide `IUserAllQueryRepository`), all implemented by a single `UserQueryRepository` class using `IDbConnectionFactory` + raw SQL. Follow this split (new interface per query feature, one class implementing all of them) rather than one fat repository interface.
